# 414 S1 Backbone — Developer Reference

## What This Is

The S1 backbone is the shared integration layer that all Sprint 1 components (enrichment, grading, delivery, billing, reporting) read and write through. It establishes two primitives:

1. **`prospects`** — canonical UUID identity record for every distressed property owner that enters the enrichment pipeline
2. **`events`** — append-only transactional outbox that carries all inter-component state changes

No S1 component is permitted to call another directly. All state transitions go through the event bus.

Branch: `feat/414-s1-m1-backbone`

## Database Schema

### `prospects`

Thin identity bridge over the existing `properties` hub. Does **not** duplicate name, address, or phone — those stay in `properties`, `owners`, and `enriched_contacts`. Join through `property_id` to read identity fields.

| Column | Type | Notes |
|---|---|---|
| `prospect_id` | UUID PK | Generated by `generate_uuidv7()` — time-ordered, sequential B-tree inserts |
| `property_id` | INT FK → properties.id | UNIQUE. One prospect per property |
| `contactability_state` | VARCHAR | `unknown` → `enriching` → `contactable` / `exhausted` / `invalid` |
| `channel_consent` | JSONB | Per-channel consent flags: `{"sms": true, "email": false, ...}` |
| `contact_attempts` | INT | Rolling outbound touch count (written by M10 Lead Delivery) |
| `successful_contacts` | INT | Rolling two-way confirmation count (written by M10) |
| `contactability_rate` | NUMERIC(5,4) GENERATED | `successful_contacts / contact_attempts` — NULL until ≥5 attempts |
| `cohort_key` | VARCHAR | `grade_band × county × source` — cohort rate fallback (not yet computed) |
| `last_touch_at` | TIMESTAMPTZ | Most recent outreach timestamp |
| `merged_into_id` | UUID FK → prospects | Set when this prospect is absorbed into another via merge |
| `created_at` / `updated_at` | TIMESTAMPTZ | Standard |

**Indexes:**
- `idx_prospects_property_id` — FK lookup
- `idx_prospects_contactable` — partial on `contactability_state = 'contactable'` — used by M10 routing
- `idx_prospects_cohort` — partial on `cohort_key IS NOT NULL`
- `idx_prospects_merged_into` — partial on `merged_into_id IS NOT NULL`

---

### `events`

Append-only. Events are immutable once written — no updates, no deletes.

| Column | Type | Notes |
|---|---|---|
| `event_id` | UUID PK | Generated by `generate_uuidv7()` |
| `prospect_id` | UUID FK → prospects | NOT NULL — every event must reference a prospect |
| `event_type` | VARCHAR | Constrained by CHECK (see allowed types below) |
| `actor` | VARCHAR | User ID, system name, or component that caused the event |
| `payload` | JSONB | Type-specific body |
| `occurred_at` | TIMESTAMPTZ | UTC |
| `source_component` | VARCHAR | Which component emitted the event |

**Allowed event types (CHECK constraint):**
`prospect.created`, `enrichment.completed`, `enrichment.failed`, `cds.scored`, `truth.verdict`, `lane.entry`, `lane.advance`, `lane.stall`, `lane.close`, `broker.transition`, `sms.sent`, `sms.reply`, `commission.posted`, `delivery.sent`

**Indexes:**
- `idx_events_prospect_id`, `idx_events_occurred_at`, `idx_events_type`

---

### `processed_events`

Idempotency guard. Every consumer inserts here before processing. Re-delivered events with a seen `(event_id, consumer)` pair are skipped.

| Column | Type | Notes |
|---|---|---|
| `event_id` | UUID FK → events | Composite PK with consumer |
| `consumer` | VARCHAR | Consumer name, e.g. `"truth_engine"`, `"lead_delivery"` |
| `processed_at` | TIMESTAMPTZ | When the consumer handled it |

---

### `merge_events`

Audit log for prospect merges. Never deleted.

| Column | Type | Notes |
|---|---|---|
| `merge_id` | UUID PK | Generated by `generate_uuidv7()` |
| `surviving_id` | UUID FK → prospects | The prospect that absorbs the other |
| `merged_id` | UUID FK → prospects | The prospect being absorbed (`merged_into_id` set on this row) |
| `field_decisions` | JSONB | Reason and field-level merge decisions |
| `merged_at` | TIMESTAMPTZ | When the merge happened |

## UUIDv7 Function

All UUID PKs use `generate_uuidv7()` — a PL/pgSQL function installed by fa087. UUIDv7 embeds a millisecond-precision timestamp in the leading 48 bits, making them time-ordered. This matters for B-tree indexes: sequential inserts avoid page splits and keep index pages hot in `shared_buffers`.

Do not use `gen_random_uuid()` for backbone PKs.

## How the Event Bus Works

The event bus is a **transactional outbox** — events are written to the `events` table in the same DB transaction as the state change that caused them. If the transaction rolls back, the event is never written. This guarantees atomicity with no external message broker.

**Emit an event:**
```python
from src.services.event_bus import emit_event

emit_event(
    session,
    event_type="enrichment.completed",
    actor="cascade",
    source_component="skip_trace_waterfall",
    prospect_id=prospect_id,   # UUID str — required
    payload={
        "property_id": 12345,
        "contactability_state": "contactable",
        "enriched_contact_id": 99,
        "source": "tracerfy",
        "confidence": 0.82,
        "total_cost_cents": 2,
    },
)
session.commit()   # event is durable only after commit
```

**Consume idempotently:**
```python
from src.services.event_bus import is_processed, mark_processed

CONSUMER = "truth_engine"

if is_processed(session, event_id, CONSUMER):
    return  # already handled — skip

# ... do work ...

mark_processed(session, event_id, CONSUMER)
session.commit()
```

## `prospect_service.py` API

### `get_or_create_prospect(session, property_id) → str`
Returns `prospect_id` (UUID str). Creates the prospect if absent using `ON CONFLICT (property_id) DO NOTHING` — race-safe. Does **not** emit `prospect.created` — see Deferred section.

### `get_prospect(session, prospect_id) → dict | None`
Canonical read. Resolves through the merge chain (recursive CTE) so callers always get the surviving record. Returns a flat dict with prospect fields + property address + owner name + best enriched contact.

```python
p = get_prospect(session, prospect_id)
# p["contactability_state"]
# p["channel_consent"]
# p["property"]["address"]
# p["owner"]["name"]
# p["enriched_contact"]["mobile"]
# p["enriched_contact"]["confidence"]
```

Returns `None` if prospect does not exist.

### `merge_prospects(session, surviving_id, merged_id, field_decisions)`
Sets `merged_id.merged_into_id = surviving_id`, writes `merge_events` row. Does **not** re-point existing events to the surviving prospect — deferred to M10.

### `dedupe_after_cascade(session, property_ids)`
Mobile-based dedup. After cascade, if two active prospects share a validated mobile, the older (`created_at`) one survives and the newer is merged. Call this after the M2 event emission loop.

### `update_consent(session, prospect_id, channel, granted)` *(not yet built — planned for M8)*
Merges `{channel: granted}` into `prospects.channel_consent`. When `granted=False` for `sms`, also calls `sms_compliance.record_opt_out()`.

## M2 Cascade Hook — How It Works Today

The cascade (`run_cascade()` in `skip_trace_waterfall.py`) runs via cron at 07:30 UTC. It selects candidates directly from `owners` / `distress_scores` (Gold+ tier, no phone, not already traced), runs providers in cost order, then at the end:

1. Fetches `property_id` for each processed owner
2. Calls `get_or_create_prospect(session, property_id)` per property
3. Stamps `contactability_state`:
   - `contactable` if any provider hit confidence ≥ 0.70 (sprint 1 proxy — see below)
   - `exhausted` if all providers failed to reach threshold
4. Fetches the best enriched contact via `best_ec(session, property_id)`
5. Emits `enrichment.completed` or `enrichment.failed` per prospect
6. Calls `dedupe_after_cascade()` to mobile-dedup new prospects
7. Single `session.commit()` — all prospect stamps and events are durable together

**Confidence threshold:** `skip_trace_confidence_threshold` in settings (default 0.70). Computed by `compute_confidence()` in `skip_trace_result.py` from presence of mobile, landline, email, mailing address, and phone reachability score.

## Architectural Decisions

### Thin-bridge prospects (not denormalized)
`prospects` does not duplicate name, address, phone, or email from `properties`/`owners`/`enriched_contacts`. These fields are available via `get_prospect()` which joins all three. This keeps the existing pipeline untouched and avoids sync problems.

If a query proves too slow due to joins, denormalize specific columns at that point — do not pre-optimize.

### enrichment_provenance dropped
`enrichment_provenance` was created in fa087 and dropped in fa088. `enriched_contacts` already stores `source`, `confidence`, and `superseded_at` (for re-enrichment chain). `enrichment_usage_logs` already stores cost-per-record. Creating a third table duplicating this data was redundant.

To read provenance: join `enriched_contacts` via `property_id`. To read cost: join `enrichment_usage_logs` via `property_id`.

### No prospect_id on enriched_contacts
The existing enrichment pipeline writes to `enriched_contacts` keyed on `property_id`. Adding `prospect_id` to that table would require touching every enrichment provider (Tracerfy, BatchData, IDI, PDL). Instead, join through `prospects.property_id = enriched_contacts.property_id`. The existing pipeline is completely untouched.

### Dedupe scope — mobile only for sprint 1
Full spec §12.2 requires matching on APN+name, mobile, normalized name+address, and voter ID. Sprint 1 implements mobile match only — it catches the primary case (same owner, multiple properties, same phone returned by cascade). APN+name, address, and voter ID dedup require data quality work on underlying tables and are deferred.

### Sprint 1 contactability proxy
The spec §2 says use confidence ≥ 0.70 as the sprint 1 proxy for `contactable` state. This is already implemented — `resolved_ids` in the cascade is populated only when `confidence >= threshold`, so `owner_id in resolved_ids → contactable` is the correct proxy. The full formula (`successful_contacts / contact_attempts`, cohort fallback) is deferred until outreach volume exists.

## Intended Future State — Event-Driven Cascade (per ADR 0016)

The current cron + `_select_candidates()` approach is batch mode. The intended architecture (ADR 0016) is:

```
CDS scoring (07:00)
  → property first enters Gold+
    → prospect seeding cron (07:15)  ← to be built
        → creates prospect stub via get_or_create_prospect()
        → emits prospect.created
          → cascade subscribes (event consumer)
          → runs enrichment for that prospect's property
          → emits enrichment.completed / enrichment.failed
            → M6 Truth Engine subscribes
```

The nightly 07:30 batch is retained as a reconciliation sweep (picks up any event that was dropped). Both paths call the same `run_cascade()` function.

The seeding cron is the missing piece. It will live at `src/tasks/prospect_seeding.py` and is planned as part of M12 infrastructure.

## For Downstream Components

**M6 — Truth Engine:**
- Subscribe to `enrichment.completed` events
- Read enriched contact via `enriched_contact_id` (direct PK lookup on `enriched_contacts`)
- Call `get_prospect(session, prospect_id)` for contactability state and channel consent
- Emit `truth.verdict` event

**M8 — SMS Path Rewire:**
- Pass `prospect_id` to `send_sms()` for prospect-level gate
- Gate checks: `contactability_state == 'contactable'` AND `channel_consent['sms'] == True`
- Use `prospect_service.update_consent()` to withdraw consent

**M10 — Lead Delivery:**
- Query active prospects via `idx_prospects_contactable` partial index
- Increment `contact_attempts` and `successful_contacts` on `prospects` as outreach happens
- Re-point events to surviving prospect after any merge
- Emit `delivery.sent` event

**M12 — Event Consumer Reliability:**
- Use `poll_and_dispatch()` (to be built in `src/services/event_consumer.py`)
- Always call `is_processed()` before handling, `mark_processed()` after
- The `processed_events` table is the idempotency mechanism — never skip it
